# Leo Shift 도메인 설계

작성일: 2026-08-10 · 함께 보기: [service-readiness-review.md](service-readiness-review.md), [feature-spec.md](feature-spec.md)

> 이 문서는 앞선 두 문서의 모델 제안을 **대체한다.** 특히 `service-readiness-review.md` 2.1의 `calendar_members` 제안과 4.1의 "이벤트 레이어 만들지 말 것" 권고는 폐기한다. 이유는 1장에 있다.

---

## 1. 왜 헷갈리는가

설계가 안 잡히는 이유는 능력 문제가 아니라, **서로 다른 세 가지가 "공유 캘린더"라는 한 단어에 묶여 있기 때문**이다.

| 실제로 원하는 것 | 성격 |
|---|---|
| 프로젝트 인원의 휴가·부재 현황 | **사람들의 가용성을 겹쳐 보는 화면** |
| 커플·가족이 서로 일정 보기 | **서로의 캘린더를 열어주는 관계** |
| 직장 동료에겐 근무만, 가족에겐 전부 | **대상마다 다른 공개 범위** |

지금 코드는 이걸 전부 "캘린더라는 그릇에 여러 사람이 들어간다"로 풀려고 한다. 그래서 `exceptions`는 캘린더 단위인데 `leave_entries`는 사람 단위인 모순이 생겼다.

그리고 제가 앞 문서에서 제안한 `calendar_members`(캘린더 안에 멤버를 넣는 것)도 **똑같이 틀렸다.** 결정적인 반례가 방금 주신 조건에 있다.

> **"프로젝트 단위로 변경되는 인원"**

김철수가 A프로젝트에서 B프로젝트로 옮기면 어떻게 되는가?

- 캘린더가 사람을 담는 모델이라면: A프로젝트 캘린더의 김철수 데이터와 B프로젝트 캘린더의 김철수 데이터가 **따로 논다.** 휴가를 두 번 입력해야 하고, 근무 패턴도 두 번 설정해야 한다. 프로젝트를 세 개 겸하면 세 번이다.
- 게다가 프로젝트를 옮긴 뒤 A프로젝트의 **과거 기록**이 어떻게 돼야 하는지도 답이 없다.

**김철수의 휴가는 프로젝트의 것이 아니라 김철수의 것이다.** 어느 프로젝트에 있든 8월 15일에 연차면 연차다. 이 사실이 설계의 출발점이어야 한다.

## 2. 핵심 원칙

> **캘린더는 사람의 것이고, 그룹은 그릇이 아니라 화면이다.**

- **개인 캘린더가 진실의 원천이다.** 근무 패턴, 휴가, 개인 일정은 전부 그 사람의 캘린더에 있다.
- **그룹(프로젝트/팀/가족)은 데이터를 담지 않는다.** "이 사람들의 캘린더를 이 기간 동안 겹쳐서 보여줘"라는 **뷰의 정의**일 뿐이다.
- **공유는 관계다.** 내 캘린더를 누구에게 어느 수준까지 열어줄지의 문제다.

이 원칙 하나로 앞의 모순들이 전부 풀린다.

| 상황 | 어떻게 되는가 |
|---|---|
| 김철수가 프로젝트를 옮김 | 멤버십만 바뀐다. 휴가·근무는 원래 자기 캘린더에 있으니 **그대로 따라간다** |
| 프로젝트를 세 개 겸함 | 세 그룹에 속할 뿐, 입력은 한 번 |
| 작년 프로젝트 기록을 봄 | 멤버십에 기간이 있으니 **그때 있던 사람들로** 정확히 재현된다 |
| 커플이 서로 봄 | 2인 그룹. 특별한 기능이 아니라 같은 구조의 인원수가 적은 경우 |
| 프로젝트에서 나감 | 내 캘린더는 그대로. 그 그룹에서만 안 보이게 됨 |

## 3. 모델

```
User
 └─ owns ─> Calendar (여러 개)
              ├─ kind: WORK | GENERAL
              ├─ [WORK일 때] 근무 규칙, 근무 코드, 근무 예외
              ├─ 휴가
              ├─ 일정 (시간 있음)
              └─ 외부 캘린더 구독

Group  (프로젝트 / 팀 / 가족 / 커플)
 ├─ Membership (user, 시작일, 종료일)   ← 기간이 핵심
 └─ owns ─> Calendar (그룹 공동 일정용, 선택)

Share  Calendar ──> User 또는 Group
        ├─ 권한: 보기 | 편집
        └─ 공개 단계: 근무만 | 바쁨만 | 전체
```

### 3.1 캘린더는 사용자당 여러 개, 공개는 단계로

사용자가 실제로 생각하는 건 "캘린더를 몇 개 만들까"가 아니라 **"누구에게 어디까지 보여줄까"**다. 그래서 저장 구조와 공유 UI를 분리한다.

**저장 구조** — 사용자당 캘린더 여러 개 (구글 캘린더와 같은 구조)

| 캘린더 | 종류 | 담기는 것 | 어떻게 채워지나 |
|---|---|---|---|
| **내 근무** | `WORK` | 근무 일정, 근무 예외, 휴가 | **규칙에서 자동 생성** |
| **내 일정** | `GENERAL` | 개인 약속, 메모, 병원, 모임 | 손으로 입력 |
| (추가) | `GENERAL` | 취미, 사이드 프로젝트 등 | 손으로 입력 |

**공유 UI** — 단계로 제시 (자세한 건 3.3)

| 공개 단계 | 실제로 공유되는 것 | 대상 예 |
|---|---|---|
| **근무만** | `WORK` 캘린더 | 직장 동료, 프로젝트 팀 |
| **바쁨만** | 전부, 단 제목 감춤 | 친구 |
| **전체** | 내 캘린더 전부 | 배우자, 가족 |

(원하는 사람은 캘린더별로 직접 고를 수 있게 두되, 기본은 이 단계들이다.)

**분류 부담이 없다는 게 이 구조의 핵심이다.** 근무 캘린더는 교대 패턴이나 요일 규칙에서 **자동으로 채워지므로** 사용자가 "이 일정을 어느 캘린더에 넣지?"를 고민할 일이 없다. 손으로 만드는 건 전부 개인 캘린더로 가는 게 기본이고, 일정을 만들 때 "직장에도 공개" 정도만 고를 수 있게 해두면 된다.

**본인 화면에서는 항상 전부 겹쳐 보인다.** "개인 일정 캘린더에 근무 스케줄도 포함된다"는 건 저장이 합쳐져 있다는 뜻이 아니라, **내 화면은 내 캘린더 전부의 합성**이라는 뜻이다. 분리는 공유할 때만 의미가 있다.

`WORK` 종류의 캘린더에만 근무 규칙이 붙는다. 사용자당 보통 하나다.

### 3.2 그룹 멤버십에 기간이 있다

```
group_members(group_id, user_id, role, joined_on, left_on)
```

`left_on`이 있는 게 핵심이다. 프로젝트 뷰를 8월로 열면 **8월에 소속돼 있던 사람들만** 나온다. 6월에 나간 사람은 6월 화면에는 나오고 8월 화면에는 안 나온다.

"프로젝트 단위로 변경되는 인원"이 이 한 줄로 해결된다. 사람을 지우는 게 아니라 종료일을 적는 것이다.

### 3.3 공유 = 대상 × 공개 단계

공유 한 건은 이렇게 읽힌다.

> **누구에게** (사람 또는 그룹) — **무엇을** (근무만 / 전체) — **어떻게** (보기 / 편집)

같은 사람이 여러 그룹에 속할 수 있고, 그룹마다 공개 단계가 다르다. 예를 들어 한 사람이:

- `OO프로젝트` 그룹에 **근무만 · 보기**
- `직장` 그룹에 **근무만 · 보기**
- `가족` 그룹에 **전체 · 보기**
- 배우자에게 개인 직접 공유로 **전체 · 편집**

**권한은 `보기`가 기본이고 `편집`은 예외다.** 남의 캘린더를 편집할 일은 사실상 없다 — 팀 근무표를 대신 만드는 시나리오를 빼기로 했으므로(4.4), `편집`이 필요한 건 그룹이 공동으로 소유한 캘린더 정도다.

공개 단계는 **세 개**다.

| 단계 | 보이는 것 | 쓰이는 곳 |
|---|---|---|
| **근무만** | 근무 캘린더만 (개인 일정 제외) | 직장, 프로젝트 |
| **바쁨만** | 시간대에 "바쁨"만, 제목 없음 | 친구 |
| **전체** | 제목·메모까지 전부 | 배우자, 가족 |

`바쁨만`이 필요한 이유는 단순하다 — **개인 일정 제목에는 남에게 보이면 안 되는 게 들어간다.** "14:00 병원", "김부장님 면담", "김철수 수업". 시간이 차 있다는 건 알려주되 내용은 감추고 싶은 경우가 누구에게나 있다.

다만 **1차 구현은 선택이다.** 직장·프로젝트에 `근무만`으로 공유하면 개인 일정은 애초에 안 나가므로 대부분 해결된다. `바쁨만`은 "친구들아 나 이번 주 언제 시간 돼?"를 위한 것이고, 스키마 컬럼만 미리 두면 나중에 붙일 수 있다.

> 앞 문서에서 **빼기를 권했던 "공유 그룹"이 여기서 부활한다.** 다만 성격이 다르다. 지금 코드의 공유 그룹은 "권한을 묶어서 주는 장치"였고, 여기서는 **프로젝트·직장·가족·친구 같은 관계 그 자체**다. 그래서 전용 화면과 기간(멤버십)이 따라붙는다.
>
> 대신 지금 구현의 문제는 그대로 고쳐야 한다 — 멤버가 스스로 나갈 수 있어야 하고, 권한이 더해지기만 하는 성질(거절을 무효화하고 개인을 보기 전용으로 낮출 수 없는 것)을 깨야 한다.

### 3.4 휴가는 캘린더에 붙는다

```
leaves(calendar_id, start_date, end_date, leave_type, note)
```

지금 구조(`calendar_leave_entries`에 `target_user_id`)와 달리, **캘린더가 이미 한 사람의 것이므로 대상 사용자 컬럼이 필요 없다.** 날짜 범위로 두면 "8/15~8/20 휴가"를 한 줄로 넣을 수 있다.

프로젝트 그룹에서 휴가 현황을 보는 것은 **멤버들의 캘린더에서 휴가를 모아 오는 조회**일 뿐, 별도 저장이 없다.

## 4. 사용 사례 검증

### 4.1 프로젝트 인원 휴가 현황 (원래 목적)

1. "OO프로젝트" 그룹을 만들고 인원을 추가한다.
2. 각자 초대를 수락하면서 **`근무만 · 보기`**로 공개한다. (기본값)
3. 그룹 화면에서 **그룹 타임라인 뷰**를 본다.

```
8월 2주차       11(월) 12(화) 13(수) 14(목) 15(금)
─────────────────────────────────────────────────
김철수                              연차   연차
이영희                                     반차
박민수(교대)     야     야     휴     휴
정수진           ·      ·      ·      ·      ·
─────────────────────────────────────────────────
가용 인원         3      3      3      2      1
```

맨 아랫줄의 **가용 인원 수**가 실제로 보고 싶은 값이다. "다음 주 목·금에 두 명 빠지네"를 한눈에 본다.

7월로 넘기면 그때 소속이던 사람들로 자동으로 바뀐다. **누구도 남의 근무를 편집하지 않는다 — 각자 자기 것을 관리하고, 이 화면은 보기 전용이다.**

같은 화면이 그룹 종류만 바꿔서 그대로 쓰인다.

| 그룹 | 이 화면에서 보는 것 |
|---|---|
| 프로젝트 | 이번 주 가용 인원, 누가 언제 빠지나 |
| 직장 | 동료들의 근무·연차 |
| 친구 | 누가 언제 시간이 되나 |
| 가족 | 서로의 근무와 일정 |

### 4.2 개인 캘린더를 선별해서 공개

같은 사람이 대상마다 다른 단계로 공개한다.

- `직장` 그룹 → **근무만**. 동료는 내 근무와 연차만 본다. "14:00 병원"은 안 보인다.
- 배우자 → **전체**. 근무와 개인 일정·메모까지 전부 본다.
- `친구` 그룹 → **근무만**. 언제 시간이 되는지만 본다.

공개 단계를 바꾸면 즉시 반영된다. 이미 공유한 걸 나중에 좁히거나 넓힐 수 있어야 한다.

### 4.3 커플·가족

인원이 2~4명이고 공개 단계가 `전체`인 그룹이다. 특별한 기능이 아니라 4.1과 같은 구조의 작은 경우다.

가족 그룹이 캘린더를 하나 소유하면 "8/15 처가 방문" 같은 **공동 일정**도 담을 수 있다 (8장 결정 사항).

### 4.4 일반 근무자가 메인 캘린더로 사용

`WORK` 캘린더에 "월~금 09:00–18:00" 요일 규칙을 한 번 걸어두고, 나머지는 전부 `GENERAL` 캘린더에 일정으로 쌓는다. 배우자가 교대근무자라면 배우자의 근무가 겹쳐 보인다.

> **팀 근무표 관리(조장이 조원 근무표를 대신 작성)는 범위에서 제외한다.** 각자 자기 근무는 자기가 관리하고, 그룹은 서로의 것을 **보는** 장치다. 이 결정으로 "계정 없는 관리 대상 사용자", "남의 근무 캘린더 편집 권한"이 함께 빠진다.
>
> 다만 프리셋의 **"몇 조인가요?"는 남는다.** 팀 관리 기능이 아니라 **개인이 자기 시작일을 쉽게 정하는 방법**이기 때문이다 — "4조 3교대의 2조"라고 고르면 기준일이 자동 계산된다.

### 4.5 시간 단위 일정 — 과외 교사 사례

개인 과외 교사처럼 **시간별 수업이 있는 사람**의 하루는 이렇게 생겼다.

```
화요일   19:00–20:00  이OO 수업
         20:30–21:30  김OO 수업
         22:00–23:00  박OO 수업
```

시작 시각이 정각이 아니고, 상대마다 요일·주기·기간이 다르다.

#### 별도 기능이 아니라 이벤트 레이어 그 자체다

이건 "과외 교사용 기능"이 아니다. **일반 사용자가 자기 일정을 적는 것과 같은 기능**이고, 다만 과외 교사가 그 기능을 가장 빡세게 쓰는 사용자일 뿐이다.

그래서 이 사례의 쓸모는 따로 만드는 게 아니라, **이벤트 레이어의 설계 기준으로 삼는 것**이다. 여기서 굴러가면 나머지 사용자는 자동으로 커버된다.

| 이 사례가 요구하는 것 | 일반 사용자에게도 필요한가 |
|---|---|
| 임의 시각 (20:30–21:30, 정각 아님) | ✓ |
| 주간 반복이 여러 개 동시에 | ✓ |
| 하루에 여러 건 연달아 → **주간 시간표 뷰**, 겹침 표시 | ✓ |
| **개별 회차만 취소·이동** (휴강·보강) | ✓ "이번 주 회의만 시간 변경" |
| 반복의 시작일·종료일 | ✓ |

전부 "제대로 만든 반복 일정"이면 나오는 것들이다. 특수 기능이 하나도 없다.

#### 근무 규칙(3.1)과는 다른 원시 타입이다

시간 일정은 교대 근무 규칙(주기 + 시퀀스)으로 풀면 안 된다.

| | 교대 근무 | 시간 일정 |
|---|---|---|
| 단위 | 하루에 하나 | 하루에 여러 개, 시각이 제각각 |
| 반복 | 전체가 한 덩어리로 순환 | 일정마다 따로 반복 |
| 시작·종료 | 패턴 하나가 계속 | 건마다 다름 |
| 변경 | 드물다 | 개별 회차 변경이 잦다 |

**근무는 `주기 + 시퀀스`, 일정은 `RRULE`.** 두 개의 원시 타입을 두는 게 맞고, 억지로 합치면 양쪽 다 나빠진다.

#### 개별 회차 예외

반복 중 특정 회차만 취소하거나 옮기는 것이다. iCalendar의 `RECURRENCE-ID` 방식 그대로, **예외가 생긴 회차만** 저장한다.

```
event_occurrences(
  event_id, original_start,     -- 몇 회차인지 식별
  status,                       -- CANCELLED | MOVED | MODIFIED
  starts_at, ends_at, title, note
)
```

취소를 **삭제가 아니라 상태로 남기는 게 낫다.** 달력에서 "이날은 휴강"으로 표시할 수 있고, 나중에 되돌리기도 쉽다.

#### 조건이 바뀔 때

"김OO 수업을 다음 달부터 20:30 → 21:00으로"는 **기존 반복을 이번 달까지로 끝내고 새 반복을 시작**하는 것으로 처리한다. 지난 기록이 그대로 남는다.

근무 규칙의 `effective_from` / `effective_to`(3장)와 같은 원리다. 과거 보존이라는 요구가 두 곳에서 같은 모양으로 나온다.

#### 지금 만들지 않는 것

앞선 초안에서 여기에 상대(학생) 엔티티, 상대별 집계, 월 정산, 학생 공유를 넣었는데 **전부 뺀다.** 요구된 건 "교사가 자기 일정을 확인하는 것"이고, 그건 일정 제목에 이름을 적는 것으로 끝난다.

나중에 "학생별로 이번 달 몇 회 했는지" 같은 요구가 실제로 나오면 그때 `events`에 대상 컬럼을 붙이면 된다. 지금 만들 근거가 없다.

## 5. 방향이 바뀐 것

주신 조건 때문에 앞 문서의 판단 두 개가 뒤집힌다.

### 5.1 이벤트 레이어를 만든다 (feature-spec 4.1의 해석 A)

"일반 근무자도 메인 캘린더로 쓰게 한다"는 목적이면 **시간 있는 일정은 선택이 아니라 전제다.** 앞 문서에서 "만들지 말고 구글 캘린더 구독으로 대체하라"고 한 건 소수 지인용이라는 전제에서 나온 결론이었고, 그 전제가 바뀌었다.

따라서 되살아나는 것들:

- 일정 생성·수정 (제목, 시간, 장소, 메모)
- 반복 일정 (RRULE) + 반복 중 특정 회차만 수정·삭제
- 주 뷰 / 일 뷰
- 일정별 알림
- 종일 일정, 여러 날 걸친 일정

**다만 냉정하게 볼 부분이 있다.** 여기까지 오면 구글 캘린더와 정면으로 비교된다. 일반 캘린더 기능은 **차별점이 아니라 기본 요건**이고, 잘 만들어도 "구글만큼 한다"가 최선이다.

이 앱의 진짜 무기는 구글이 못 하는 두 가지다.

1. **교대 근무 패턴을 제대로 다루는 것** — 프리셋, 조 지정, 주기 미리보기
2. **팀 부재 현황을 한눈에 보는 것** — 4.1의 타임라인 뷰

일반 캘린더 기능은 "이탈하지 않을 만큼"만 만들고, 위 두 가지에 완성도를 몰아주는 게 맞다고 본다.

### 5.2 확장을 전제로 되돌리는 것들

사용자가 늘어난다면 앞 문서 0.1에서 후순위로 내렸던 것 중 아래는 다시 올라온다. 다만 **지금 당장이 아니라, 늘어나기 시작할 때**다.

| 항목 | 언제 필요해지는가 |
|---|---|
| 회원가입 레이트 리밋 | 가입을 공개하는 시점 |
| 계정 삭제 / 데이터 내보내기 | 모르는 사람이 쓰기 시작하는 시점 |
| 이용약관 / 개인정보처리방침 | 위와 같음 |
| XSS 전면 대응 + CSP | 서로 모르는 사람이 같은 그룹에 들어가는 시점 |
| 감사 로그 | 조직 단위 도입이 생기는 시점 |
| 접근성 | 사용자층이 넓어질수록 |

**지금 해야 할 것은 이것들을 만드는 게 아니라, 나중에 못 만들게 막지 않는 것이다.** 구체적으로는 스키마에 `deleted_at` 자리를 비워두고, 사용자 삭제를 막는 FK를 만들지 않고, 렌더링을 자동 이스케이핑되는 방식으로 짜는 것 정도다.

## 6. 스키마 초안

```sql
users(id, email UNIQUE(lower), name, ..., created_at, deleted_at)

calendars(
  id,
  owner_user_id  → users,     -- 둘 중 하나만
  owner_group_id → groups,
  name, color, timezone,
  kind,          -- WORK | GENERAL
  is_default,
  created_at, updated_at, deleted_at
)

-- 근무 (kind=WORK)
schedule_types(id, calendar_id, code, name, color,
               start_time, end_time, counts_as_work, sort_order)
   UNIQUE(calendar_id, code)

work_rules(id, calendar_id,
           anchor_date, cycle_length, sequence jsonb,
           effective_from, effective_to,     -- 과거 보존
           source_preset_id)

day_overrides(id, calendar_id, date, schedule_type_code,
              note, author_user_id, updated_at, version)
   UNIQUE(calendar_id, date)

leaves(id, calendar_id, start_date, end_date, leave_type,
       note, created_by_user_id, created_at, updated_at)

-- 일정
events(id, calendar_id, title, description, location,
       starts_at timestamptz, ends_at timestamptz, all_day,
       rrule, rrule_until,          -- 반복 정의 (4.5)
       created_by_user_id, created_at, updated_at, version, deleted_at)

-- 반복 중 예외가 생긴 회차만 저장 (취소·이동·개별 변경)
event_occurrences(id, event_id,
                  original_start timestamptz,   -- 몇 회차인지 식별
                  status,        -- CANCELLED | MOVED | MODIFIED
                  starts_at, ends_at, title, note,
                  created_at, updated_at)
   UNIQUE(event_id, original_start)

-- 그룹
groups(id, owner_user_id, name, kind,   -- PROJECT | TEAM | FAMILY
       created_at, updated_at, deleted_at)

group_members(id, group_id, user_id, role,   -- OWNER | MEMBER
              joined_on, left_on)             -- 기간이 핵심

-- 공유
calendar_shares(
  id, calendar_id,
  grantee_user_id  → users,    -- 둘 중 하나만
  grantee_group_id → groups,
  permission,     -- VIEW | EDIT
  visibility,     -- FULL | BUSY_ONLY
  status,         -- PENDING | ACCEPTED | REJECTED  (개인 대상만)
  created_by_user_id, created_at, updated_at
)

-- 외부 연동
external_sources(id, calendar_id, feed_url, name, color,
                 last_synced_at, last_error, active)
   UNIQUE(calendar_id, feed_url)
```

설계 시 지킬 것 (앞 문서 6장에서 걸린 것들):

- 시각은 전부 `timestamptz`, 날짜만인 것은 `date`
- `ddl-auto=validate`, Flyway V1부터 새로
- 모든 FK에 `ON DELETE` 명시 — 사용자 삭제 경로를 막지 않는다
- 동시 편집이 가능한 테이블에 `version` (낙관적 잠금)
- 근무 규칙은 `(기준일, 주기, 시퀀스)` 하나로 통일 — 요일 규칙은 주기 7인 경우일 뿐 (review 3.1)

## 7. 화면

| 화면 | 내용 | 우선순위 |
|---|---|---|
| **월 달력** | 내 캘린더들을 겹쳐서. 근무 + 일정 | 필수 |
| **주간 시간표** | 시간축 자유 배치. 일반 일정 + 수업 | 필수 (5.1, 4.5) |
| **날짜 상세** | 그날의 근무, 일정, 휴가, 메모 | 필수 |
| **그룹 타임라인** | 멤버 × 날짜 격자, 하단에 가용 인원. **보기 전용** | **핵심 차별점** |
| **근무 패턴 설정** | 프리셋 → 조 선택 → 미리보기 | **핵심 차별점** |
| **그룹 관리** | 인원 추가/종료 | 필수 |
| **공유 관리** | **누구에게 어디까지 공개 중인지 한 화면에서** | 필수 |

주간 시간표는 **격자에 맞추지 않는다.** 20:30–21:30 같은 시각이 그대로 표현돼야 하므로 분 단위 절대 배치이고, 겹치는 일정은 나란히 놓는다 (4.5).

마지막 화면이 특히 중요하다. 개인 일정까지 담기는 캘린더라면 사용자는 **"지금 누가 내 뭘 보고 있지?"**를 언제든 확인하고 바꿀 수 있어야 한다. 목록은 이런 모양이 된다.

```
직장                        근무만   ▾    5명
OO프로젝트                  근무만   ▾    4명
가족                        전체     ▾    3명
김영희 (개인 공유)          전체     ▾
```

한 줄에서 바로 단계를 바꾸거나 공유를 끊을 수 있어야 한다. 지금 코드에는 **공유를 취소하는 기능 자체가 없다.**

## 8. 남은 결정

1. **그룹이 캘린더를 소유하게 할 것인가?** — 가족 공동 일정("처가 방문")이 필요하면 필요하다. 없으면 `owner_group_id`를 빼고 단순화할 수 있다. **넣는 쪽을 권한다** — 나중에 추가하는 게 더 어렵다. 그룹 캘린더가 `편집` 권한이 실제로 쓰이는 유일한 자리이기도 하다.
2. **조직/회사 개념이 필요한가?** — "프로젝트"가 회사 안에 있는 구조라면 언젠가 상위 개념이 필요하다. 지금은 그룹만으로 시작하고, 그룹에 상위 그룹을 붙일 수 있게 열어두는 정도면 충분하다고 본다.
3. **휴가 종류를 사용자가 정의할 수 있게 할 것인가?** — 지금은 연차/오전반차/오후반차 고정이다. 회사마다 다르므로(경조사, 대체휴무, 무급) 근무 코드처럼 사용자 정의로 가는 게 자연스럽다. **그룹 타임라인에서 "누가 왜 없는지"를 보는 게 원래 목적이므로 우선순위가 낮지 않다.**
4. **그룹 초대 시 공개 단계를 누가 정하는가?** — 그룹 만든 사람이 "이 그룹은 근무만"이라고 정하는 방식과, 참여자가 각자 고르는 방식이 있다. **참여자가 정하되 그룹이 기본값을 제안하는 쪽**을 권한다. 내 캘린더를 어디까지 보여줄지는 남이 정할 일이 아니다.
5. **`바쁨만` 단계를 1차에 구현할 것인가?** — 스키마 컬럼은 처음부터 두되, 화면 구현은 미뤄도 된다 (3.3).
6. **반복 일정의 RRULE을 어디까지 지원할 것인가?** — 매일·매주·격주·매월·매년이면 실사용의 대부분이다. "매월 셋째 주 화요일" 같은 건 뒤로 미뤄도 된다. 다만 **저장은 표준 RRULE 문자열로** 해두면 나중에 넓히기 쉽고 ICS 내보내기와도 바로 맞는다.

## 9. 이 설계에서 다시 짠 순서

앞 문서 7장의 로드맵을 이 모델에 맞춰 조정한 것이다.

**0단계 — 이관 전 필수** (변동 없음)
보안 항목(SSRF, JWT 시크릿, db-stats, 토큰 타입), 홈서버 인프라, 백업. `service-readiness-review.md` 7장 참조.

**1단계 — 뼈대**
사용자 · 캘린더(여러 개) · 단발 일정 · 근무 규칙 · 휴가 · 월 달력. 그룹 없이 **개인 캘린더만으로 완결**되게 만든다. 이 단계에서 이미 "혼자 쓰는 캘린더"로는 완성품이어야 한다.

**2단계 — 근무 패턴 완성**
프리셋 딕셔너리, 조 선택, 달력 미리보기, 순서 편집, 유효기간. 교대근무자에게 처음으로 쓸 만해지는 지점.

**3단계 — 그룹과 공유** ← 원래 목적
그룹(프로젝트·직장·가족·친구), 기간 있는 멤버십, 공유(대상 × 공개 단계), 공유 관리 화면, **그룹 타임라인 뷰**.

> 여기를 세 번째에 두는 이유: 프로젝트 부재 현황에 필요한 건 **근무 규칙과 휴가뿐**이고, 그건 2단계에서 이미 완성된다. 일정·수업 기능을 기다릴 필요가 없다.

**4단계 — 반복 일정과 시간표** (4.5)
RRULE 반복, 반복 시작·종료일, **주간 시간표**(분 단위 배치, 겹침 표시), 회차 예외(`event_occurrences`). 과외 교사 사례를 기준으로 만들면 일반 사용자는 자동으로 커버된다.

**5단계 — 메인 캘린더로 쓰이기 위한 나머지**
일정 알림, 근무 전 알림, ICS 양방향, 오프라인, 다크 모드.

**6단계 — 확장 대비**
5.2의 항목들. 사용자가 실제로 늘기 시작할 때.

> 순서의 핵심은 **1→2에서 개인용으로 완성한 뒤 3에서 공유를 얹는 것**이다. 지금 코드는 공유를 먼저 만들고 개인 경험이 비어 있어서, 혼자 써도 불편하고 같이 써도 안 되는 상태가 됐다.
>
> **4단계는 1~3과 독립적이다.** 시간 일정 쪽을 먼저 잡고 싶다면 순서를 바꿔도 구조가 깨지지 않는다.
