# 스키마 (migration-next)

`docs/domain-design.md` 설계를 구현한 스키마다. `application.properties`의
`spring.flyway.locations`가 이 경로를 가리킨다.

기존 `db/migration/`의 V1~V11은 재작성과 함께 삭제했다. 옛 스키마가 필요하면
커밋 `49433ff` 이전 히스토리에서 꺼낼 수 있다.

## 전제

**빈 데이터베이스에 적용한다.** 기존 서비스 데이터는 가져오지 않기로 했다
(사유: `docs/service-readiness-review.md` 7장). 운영 DB에는 테스터 8명과
`exceptions` 0건뿐이었고, 마이그레이션을 짜는 비용이 데이터를 다시 넣는 비용보다 컸다.

더 중요한 이유는 "기존 데이터를 받아와야 한다"는 제약이 새 설계를 오염시킨다는
점이었다. 존재하지도 않는 데이터를 위해 모델을 타협할 이유가 없었다.

Hibernate는 스키마를 건드리지 않는다 (`ddl-auto=validate`). 이전 설정은 `update`였고,
Flyway와 동시에 쓰면서 운영과 로컬 스키마가 조용히 어긋났다.

## 요구 사항

- PostgreSQL 13 이상 (`gen_random_uuid()` 내장, `num_nonnulls()`)
- `btree_gist` 확장 — `work_rules`의 유효기간 겹침 방지에 필요.
  공식 postgres 이미지에는 contrib이 포함돼 있어 별도 설치가 필요 없다.

## 검증

`postgres:16-alpine`에 적용해서 아래를 확인했다.

- 전체 DDL 적용 성공
- 제약 24건이 의도대로 동작 (막아야 할 것은 막고, 허용해야 할 것은 통과)
- 접근 권한·멤버십·근무 규칙 조회가 전부 인덱스를 탐

```sh
docker run -d --name pgtest -e POSTGRES_PASSWORD=test -e POSTGRES_DB=t -p 55433:5432 postgres:16-alpine
docker exec -i pgtest psql -U postgres -d t -v ON_ERROR_STOP=1 < V1__init_schema.sql
```

## 설계상 알아둘 것

**하루의 근무를 정하는 순서**

```
work_rules (반복 규칙) → leaves (휴가 범위) → day_overrides (날짜별 예외)
```

뒤가 앞을 덮어쓴다.

**`work_rules`는 유효기간이 겹칠 수 없다** (`work_rules_no_overlap`).
기존 코드에서 월 뷰와 일 상세가 서로 다른 근무를 보여준 원인이 겹침이었다.
구조적으로 막아두면 "그날의 규칙"이 항상 하나로 정해진다.

**일정 타입 코드 이름 변경은 DB가 처리한다.**
`leaves`와 `day_overrides`는 `schedule_types(calendar_id, code)`로 복합 FK를 걸고
`ON UPDATE CASCADE`를 준다. 코드를 바꾸면 참조가 자동으로 따라오고,
사용 중인 코드는 `ON DELETE RESTRICT`로 삭제가 막힌다.
기존 `ScheduleTypeService`가 임시 코드를 만들어 우회하던 로직이 통째로 필요 없어진다.

**단, `work_rules.code_sequence`는 JSONB라 FK가 걸리지 않는다.**
코드 이름 변경·삭제 시 이 컬럼은 애플리케이션이 함께 갱신해야 한다.
정규화(슬롯 테이블)하면 FK로 처리되지만, 시퀀스는 항상 통째로 읽고 쓰므로
단순함을 택했다. 무결성을 더 원하면 슬롯 테이블로 바꿔도 된다.

**`calendar_shares` 조회에는 반드시 `status = 'ACCEPTED'`를 넣을 것.**
핫패스 인덱스가 그 조건의 부분 인덱스다. 빠뜨리면 seq scan이 된다.
(기존 스키마가 정확히 이 실수를 했다.)

**`GENERATED BY DEFAULT AS IDENTITY`를 쓴다.**
JPA `GenerationType.IDENTITY`와 맞고 테스트에서 id를 직접 넣을 수 있다.
다만 id를 명시해서 넣으면 시퀀스가 따라 올라가지 않으므로, 시드 데이터를 넣었으면
`SELECT setval(pg_get_serial_sequence('users','id'), max(id)) FROM users;` 로 맞춰야 한다.
